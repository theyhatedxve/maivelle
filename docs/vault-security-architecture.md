# Phase 11 cryptographic gate — candidate design

Status: **historical candidate design, subsequently implemented and tested with fictional credentials**. The loading investigation identified JavaScript scrypt scheduling starvation. A background native KDF passed public-fixture checks on HONOR; see [the investigation](phase-11-crypto-investigation.md). See [the implemented protocol and limits](vault.md) and [current verification](phase-11-vault-verification.md) for the authoritative implementation status. The proposal below is retained for review context, not as a production-security claim. The production `ENCRYPTION_REQUIRED` gate remains intact; only fictional credentials may be used in this development build.

## Existing boundary

The repository uses Expo 58.0.16, React Native 0.88.0, expo-sqlite 58.0.13 and expo-secure-store 58.0.2. SQLCipher support is configured, but the existing development database is intentionally unkeyed; compiling SQLCipher does not encrypt it. Android backup is disabled. The process-owned connection and migration runner must remain intact. Migration 9 is the latest applied schema; a functional Vault would require a new migration 10, never edits to 1–9 or a storage reset.

Local Authentication 58.0.2 and Screen Capture 58.0.5 were already present in package.json when this phase began. Their presence does not prove they are linked into the installed APK or that biometric protection is enforced.

## Candidate primitives and key lifecycle

1. Use **only** Expo Crypto's native `getRandomBytesAsync` for random key/salt/nonce bytes. The synchronous `getRandomBytes` contains a development `Math.random` fallback and is forbidden for Vault. Native source uses Android `SecureRandom`; fail if the native module is absent.
2. Generate a fresh random **256-bit data-encryption key (DEK)**. Never derive credential encryption directly from the master password. Protect each encrypted object with AES-256-GCM, a 96-bit random nonce and a 128-bit authentication tag through Expo Crypto 58.0.7 / Android JCA.
3. Candidate wrapping KDF: **scrypt N=131072, r=8, p=1, dkLen=32**, random 32-byte salt, using Bouncy Castle `bcprov-jdk15to18:1.86` on Android through the local Expo module and `Dispatchers.Default`. Pinned `@noble/hashes` 2.2.0 is retained only for host reference tests and the bounded scheduling diagnostic. This is a reviewed alternative to Argon2id listed by OWASP. Noble's historical independent Cure53 audit covers version 1.0.0 and explicitly excludes Argon2; it does **not** certify 2.2.0 or Maivelle. Noble maintainers also advise against pure JavaScript Argon2 performance. No claim of a current-version independent audit is made. Bound input/cost/memory before derivation; reject unknown KDF/version policies rather than lowering work factors. The 128 MiB work factor matched Node/OpenSSL on HONOR in 3722 ms while JavaScript timers continued. The native adapter and proposed protocol are not independently certified.
4. Wrap the random DEK with the derived wrapping key using a fresh AES-GCM nonce. Authenticate domain, vault identity, format/KDF identifiers, salt and relevant version fields as canonical associated data. Persist only salt, supported cost/version identifiers, nonce, tag and ciphertext. No master-password hash/verifier or derived key is persisted. Wrong-password and authentication failures must not delete/reset data.
5. Credential payloads contain account name, username, email, password, website, notes, category and favorite state. All these fields must be encrypted together. SQLite item metadata should expose only opaque IDs, authenticated version/revision and timestamps, not credential labels/URLs. Associated data must bind each envelope to vault/item identity and revision to reject cross-item substitution.
6. Unlock keeps the DEK and decrypted records only in memory. Master-password changes authenticate the current master password, derive a fresh salt/wrapping key, and atomically rewrap the same DEK; they must preserve item ciphertext and records. Remove any device biometric key cache before committing a changed master wrapper, with explicit failure handling. Stale backup copies remain decryptable with their old password; warn about this limitation.
7. Optional biometrics require a completed master-password unlock first. Store the device unlock material through **SecureStore with requireAuthentication**, in an isolated keychain service bound to the vault identity/wrapper revision. Android Keystore encrypts/protects that material; a standalone LocalAuthentication success prompt must never unlock ciphertext. Require strong enrolled biometrics. Handle cancellation, lockout, unavailable hardware and invalidated keys without erasing the master wrapper. Re-enrollment requires master-password fallback and re-enablement. Do not claim SecureStore guarantees StrongBox backing on this phone without evidence.
8. Lock on background/process restart; configure a bounded inactivity timeout. Invalidate asynchronous operations with a session generation so a completed unlock/decrypt cannot repopulate a locked screen. Unmount secret forms and clear in-memory records/references, overwrite owned byte arrays where possible, and apply Android screenshot/app-switcher protection before secret rendering. JavaScript strings, keyboard buffers, native key objects and garbage collection prevent guarantees of complete memory zeroization; document that limit and prohibit secrets in debugging/logs.
9. Generator uses native random bytes with rejection sampling, validates character-set/length choices, and never uses modulo reduction without rejecting excess byte values. Clipboard actions are explicit. Never promise expiry/cleanup where Android/Expo cannot safely verify ownership of the clipboard; avoid overwriting clipboard data copied by another app. Require device verification of clipboard previews and secret-screen flags.
10. Portable backup must authenticate the entire versioned vault envelope and encrypted item manifest, including IDs/revisions/count. A separate password-derived export envelope with fresh salt/nonce can encrypt a complete vault snapshot; device-only biometric material is excluded. Validate size/version/KDF bounds and all authenticated content **before** an atomic restore. No plaintext export, fake password recovery or destructive auto-recovery. Losing the master password and all usable backups means permanent loss; device biometrics are not portable recovery.

The existing main database remains development-only; a functional encrypted-payload vault would not resolve production encryption/key management for other modules. Whether a separate production vault store should be allowed before the rest of the app is ready requires an explicit design decision, not removal of the current security gate.

## Verification before storage

`src/services/security/vaultCryptoGate.js` defines public fixtures without database writes, SecureStore writes or credential forms. It is invoked only through explicit controls on development-only `/vault-security-check`; startup and URL parameters never run cryptography. The candidate probe covers native RNG availability, RFC 7914 scrypt output, the proposed full cost on the native background dispatcher, AES-256-GCM known-answer output/decryption, ciphertext/AAD tampering and sampled nonce uniqueness. Native primitive results passed as recorded in the investigation, including wrong-key and authentication-tag rejection; this does not verify a functional Vault. Samples cannot prove absence of collisions or certify a CSPRNG.

Host tests in `tests/vault/crypto-gate.test.cjs` compare the KDF against an independent Node/OpenSSL implementation and reject unsupported input sizes. Host tests cannot establish native compatibility, biometric enforcement, screenshot protection, auto-lock or backup integrity.

The `expo-crypto` dependency and local `modules/maivelle-crypto` adapter require **local Android rebuild/install**, not a Metro-only reload (prebuild first for a fresh native project). No emulator or EAS/cloud build is used. Preserve app signing/data via replacement install; never uninstall or clear app storage for a build/migration problem. A successful build alone does not pass the runtime gate.
