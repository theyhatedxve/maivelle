## Verified results

- Installed versions read from packages: Expo **58.0.16**, SQLite **58.0.13**, SecureStore **58.0.2**; new Expo Crypto **58.0.7**, Noble Hashes **2.2.0**. Package compatibility check reports dependencies up to date.
- SDK 58 Crypto, SecureStore, LocalAuthentication and ScreenCapture documentation consulted; installed Android sources inspected for native SecureRandom, AES/GCM and Keystore authentication handling.
- The synchronous Expo `getRandomBytes` includes a development `Math.random` fallback. The candidate explicitly uses **getRandomBytesAsync**, whose installed implementation delegates to native randomness or throws. This source inspection does not replace a runtime test.
- **3/3 host cryptographic-gate tests pass**: RFC 7914 vector; full `N=131072,r=8,p=1` output matches independent Node/OpenSSL scrypt; unsupported password/salt lengths reject without changing policy.
- **137/137 existing database/module regression tests pass.**
- After quarantining the probe, **all seven existing native suites passed on the rebuilt/installed APK**: database/Notes, Tasks, Calendar, Medicine, Time Tracker, Finance and Budget. These isolated fixtures are separate from the application database. Results are recorded locally in ignored `.expo/phase11-existing-native-results.json`. They establish regression coverage for existing modules, not Vault cryptographic compatibility.
- `npm run lint`: passes with zero warnings. `npm run typecheck`: strict JavaScript/JSDoc checks pass.
- `npm run check:dependencies`: dependencies up to date. `npm run doctor`: **20/20** checks passed.
- Local `expo prebuild --platform android --no-install` completed. Local Gradle **BUILD SUCCESSFUL** in about six minutes; 506 tasks. APK: `android/app/build/outputs/apk/debug/app-debug.apk` (generated artifact, not a source file).
- The initial install stage failed with `device 'AFAM026324010734' not found`. After reconnecting, replacement installation returned **Success**. The updated app opens and displays the existing synthetic Finance balance; runtime cryptographic compatibility is still **not verified** until the probe executes successfully.
- `git -c core.safecrlf=false diff --check` passes. Formatting/type/lint errors encountered while preparing the new probe were corrected before final validation.

Build warnings: upstream Kotlin/Gradle deprecations, CMake minimum-version notices and Windows cross-volume hard links falling back to file copies. Prebuild also recommends expo-system-ui for configured user-interface style; it was not added for this security probe. These warnings did not prevent compilation.

## Dependency security findings

`npm audit` reports **26 advisories/dependency findings: 19 high, 7 moderate** across the existing Expo/React Native toolchain tree. Neither newly added crypto package appears in the report. Actual advisory roots reported are `braces` pattern nesting/stack exhaustion, `node-forge` RSA verification and `uuid` buffer bounds; many parent packages inherit the findings. This is an inventory, not proof that each issue is exploitable in the Android app, and it is not dismissed as harmless.

The audit's automatic top-level fix suggests Expo 44.0.6, incompatible with preserving SDK 58. No automatic `audit fix --force`, SDK downgrade or unrelated dependency rewrite was applied. Compatible patched dependency resolution and an exposure assessment remain security review work. Full raw output is in ignored `.expo/phase11-npm-audit.json` for local inspection. No production-secure claim is made.

## Native continuation on HONOR

Reconnection follow-up: the compiled APK is now installed. Metro was restarted on 8086 after confirming the old owned process was stale; a visible **Public probe revision 2** marker verified the current diagnostic source. An ADB server 39/41 mismatch also restarted USB forwarding; forwarding was restored before reloading. Early deep-link attempts arrived before the initial 21-second bundle finished and were repeated after startup. These transport/startup observations are not evidence of a cryptographic algorithm failure.

The dynamic-loading attempt showed `Checking loading native crypto` and did not complete. A locally bundled lazy-loading variant and an explicit development-only autorun were investigated; the current-source marker appeared, but no public-vector results followed and the user could not tap the screen. This is a runtime compatibility/loading blocker, **not proof that AES or scrypt calculations are incorrect**. Maivelle-only JavaScript/AndroidRuntime logs did not identify an exception. A process-owned SIGQUIT diagnostic did not yield a useful stack; debuggerd reported `root is required`. The phone was not rooted and security settings were not weakened. The stalled process was force-stopped without deleting data; the diagnostic UI no longer invokes cryptography, including through the old autorun URL.

Recovery verification passed: Maivelle Home loaded, the old `?autorun=1` URL displayed **Native verification blocked** without executing the probe, and an injected tap on **Go back** returned to Home. Touch navigation was responsive again. The candidate probe source remains available for controlled investigation but is not referenced by the route. This recovery does not pass the cryptographic gate.
