# SQLCipher provisioning design and disposable verification

Phase 13, 21 October 2026. **Production provisioning is not enabled.** The existing development databases remain unkeyed, and `ENCRYPTION_REQUIRED` still prevents production opening. No live conversion, key replacement or retirement has been executed.

## Ownership and key availability

`src/database/encryptedConnection.js` is an injected design/test factory, separate from the live connection manager. Explicit provisioning generates 32 random bytes, records version and database identity with the key in device-protected storage, reads the record back, then opens and keys the database before its first schema query. Opening an existing database requires both a valid key record and an existing file. Missing, malformed or wrong keys fail closed; opening never falls back to creating an empty replacement. Initialization failures retain the file and key for investigation. Overlapping calls on the same factory are rejected.

The Android probe uses a dedicated Expo SecureStore keychain service, not Vault key storage. Android Keystore protects SecureStore material on the device; this does not promise StrongBox, per-read biometric authorization, survival of uninstall or transferability. App lock and Vault master-password authorization remain separate. The random SQLCipher key is independent of the Vault data-encryption key.

Every exclusive writer must receive the same key before foreign-key PRAGMAs and `BEGIN`. The transaction adapter accepts an injected keyed writer opener. Normal development connections retain their existing behavior. SQLCipher's key PRAGMA is not bindable: the probe interpolates only validated native-random bytes encoded as hex, masks native failures and never logs the statement. JavaScript strings and native buffers cannot be reliably zeroized; owned byte arrays are cleared where possible.

## Physical verification

The HONOR development build passed eight disposable checks: encrypted file header; device-protected key reopening and schema 1-to-10 upgrade preserving a note; keyed exclusive writer and foreign keys; wrong-key rejection; missing-key rejection before native open; refusal to silently create a missing file; correct-key reopening after rejected attempts; and rejection of an empty existing file before migration initialization. Idempotent initialization was exercised. Only the probe's database and separate SecureStore record were removed, in that order. Eight host tests cover provisioning order, invalid records, overlapping provisioning, refusal to replace existing files/keys, empty/missing migration ledgers, redacted errors and retained recovery artifacts.

## Portable recovery and approval boundary

### Proposed production protocol (review required; not enabled)

The proposed production design uses **one independently random 256-bit SQLCipher key per database generation**, protected by Android Keystore through SecureStore. A versioned record binds that key to the exact generation name and cipher policy. It is not derived from the Vault master password and is not an app-lock credential. Normal database access must work without a Vault unlock. Device protection without per-read biometric authentication is the proposed policy for ordinary module/background access; it does not defend against an attacker already operating an unlocked, compromised device. Vault envelopes retain their independent master-password authorization.

1. Acquire a native process/file lock before first provisioning, key publication or generation selection. The current factory's JS instance guard is a disposable proof, not this cross-process lock. Refuse concurrent provisioning rather than generating competing keys.
2. Read the nonsensitive generation journal and SecureStore record before opening a sensitive SQLite handle. Missing/invalid records, unavailable Keystore, unexpected file state and unknown cipher policy stop opening. Never create a replacement key/database to make an error disappear. A valid key is applied immediately after the native handle opens, before any schema access, migration, WAL operation or writer transaction.
3. Explicit first provisioning uses a fresh generation identifier. Journal PREPARING, durably persist the protected key, read it back, create/key the new file, apply the unchanged migration ledger, and verify integrity and keyed reopening. Publish ACTIVE only after verification. Key loss or file/key disagreement retains both artifacts and blocks access. An orphan key/file is a recovery state requiring an explicit decision, not permission to overwrite it. SecureStore and SQLite cannot commit atomically; journal recovery must cover every boundary.
4. Every short-lived writer and staging/recovery opener uses the same keyed policy. Retained generations keep their own bound key. Close all consumers/writers before cutover. Publish the pending generation transactionally with synchronous journal durability; finalize only after reopening, exact schema/record checks and Vault authorization. Pending startup state selects the untouched previous generation. Never finalize a candidate merely because its file exists.
5. Verify Android backup exclusions for all device-bound key material. Current allowBackup=false must remain. Do not depend on Android backup transferring Keystore keys, promise StrongBox availability, or silently enable biometric key protection that can invalidate background access. New biometric authorization policies require separate enrollment/loss testing.

**Portable recovery decision:** propose a new authenticated format version using a bounded, validated logical record stream from a consistent read snapshot, encrypted with the existing full-cost native scrypt and AES-GCM backup primitives. Do not export the SQLCipher key. On another device, provision a new device-bound generation key and import into encrypted staging, preserving record IDs, timestamps and the unchanged migration history. Authenticate format/schema/KDF metadata, chunk ordering and completion. Validate allowlisted tables/columns, constraints, counts, integrity, all module records and original Vault-master unlock before cutover. Derived notification IDs and Keystore shortcuts are rebuilt, not transferred. Existing format 1 remains explicitly identified and supported only under its current development security policy; do not relabel its unkeyed snapshot pages as encrypted-at-rest production storage.

Loss behavior is explicit: a lost/invalidated device key cannot be recovered from a Vault password alone. A verified portable archive plus its backup passphrase can recover application records into a new generation; encrypted Vault records also require their original master password. Losing both the device key and usable backup makes the affected database unrecoverable. Restoring must preserve the inaccessible original as a recovery artifact until separately approved retirement; no backdoor, automatic reset or secure-flash-erasure promise is offered.

**Exact operation requiring separate approval:** add the reviewed production owner/journal/key-publication implementation and portable-format support; then create a *new* encrypted generation from the currently selected unkeyed development database, verify exact record equality, schema, balances and Vault unlock, replacement-select it through the recovery journal, and retain the untouched original and verified backup. This would change live storage selection and introduce production key material. It has **not** been executed or enabled. Retirement of plaintext generations is another separately approved operation. Before any live operation, test copied disposable fixtures with process-death and key/journal/storage failures at each boundary and obtain independent security review.

Keystore keys are device-bound and must not be copied into backups. Existing backup format 1 encrypts an unkeyed SQLite snapshot with a dedicated passphrase and full-cost native scrypt/AES-GCM; it retains encrypted Vault envelopes and requires the original Vault master password. It is not yet a portable encrypted-SQLCipher recovery implementation. A new reviewed format must specify either validated streaming logical export into a newly keyed destination or a reviewed portable database-key envelope/conversion. Authenticate schema, generation and KDF/encryption metadata. Do not export raw keys, silently change work factors, or rely on transferable Keystore material.

Before enabling production, review crash-safe multi-process provisioning/key-publication journaling, key-to-generation binding, all snapshot/staging/retained-generation openers, key-loss recovery and authenticated portable conversion. The factory's in-process guard is not a multi-process atomic provisioning protocol.

Any live encryption migration requires separate explicit approval. Convert a copied disposable fixture into a new encrypted generation first; verify record equality, migration ledger, foreign keys, balances and Vault unlock, then prove interruption/rollback behavior. Preserve the original and a verified recovery archive. Approval is also required before retiring old plaintext generations or their dependent keys. No secure flash-erasure guarantee is made. Independent security review remains required.
